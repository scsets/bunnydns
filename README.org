* Overview

** Problem

A Bunny DNS zone may contain records owned by several projects and records
maintained by hand.  A deployment needs to change its own addresses and text
records without overwriting an unrelated mail, verification, or service
record in the same zone.  Raw API calls do not preserve that boundary by
themselves.

** Solution

=dns_bunny.sh= can inspect and edit one record directly from the command line,
or own a declaration of desired records for repeatable reconciliation.  Direct
commands identify updates and deletions by Bunny's numeric record ID.  Each
declaration instead names an =owner= and gives every record a durable =key=.
The tool stores those two values in the Bunny record comment, reconciles only
matching records, and preserves every record owned by another project or by no
project.

The tool never creates or deletes a DNS zone, changes registrar delegation, or
manages DNSSEC.  It does not read credentials from the declaration or from
command-line arguments.

The reconciliation and safety policy remains a small POSIX shell program.  API
transport is delegated to =dns_bunny_node.mjs=, which uses Bunny's official
=@bunny.net/openapi-client=.  This keeps project ownership, safe pruning,
snapshots, and post-change verification in this tool while avoiding a locally
maintained HTTP implementation.

Bunny's official =@bunny.net/cli= remains useful on its supported platforms,
but its npm package launches prebuilt native binaries and the pinned 0.15.1
release has no =sunos-x64= binary.  The official OpenAPI client is pure
JavaScript, supports Node 18 or newer, and was exercised successfully in a
SmartOS native zone.  Driving that client directly therefore preserves the
same official API definitions on both macOS and SmartOS.

** How it works

1. The tool reads a protected one-line API key file and locates exactly one
   existing zone by its domain name.
2. =list= fetches and prints that zone directly; no declaration is needed.
3. =add=, =update=, and =delete= validate their CLI fields, write a protected
   snapshot, perform one explicit change, fetch the zone again, and verify
   the result.
4. File-based commands validate the declaration and normalize record types and
   optional fields into Bunny's API shape.
5. They compare desired records with the current zone using the ownership
   comment =managed-by:OWNER; key=KEY= and report safe creates, updates,
   replacements, exact matches, or conflicts.
6. =apply= writes a protected snapshot, performs only the planned changes,
   fetches the zone again, and requires a clean plan.  Explicit =prune= deletes
   obsolete records for this declaration's owner only.

** Quickstart

First run the read-only checks:

#+begin_src sh
./dns_bunny.sh
./dns_bunny.sh list ckg.re
./dns_bunny.sh validate records.example.json
gmake self-check
#+end_src

The direct command above reads =$HOME/.secrets/bunnynet-api-key=.  To select a
different protected key file, put the global option before the command:

#+begin_src sh
./dns_bunny.sh --api-key /absolute/path/to/bunny-api-key list ckg.re
#+end_src

For a one-off record, use the numeric IDs printed by =list= for later edits:

#+begin_src sh
./dns_bunny.sh add ckg.re A www 192.0.2.10
./dns_bunny.sh update ckg.re 123456 --value 192.0.2.11
./dns_bunny.sh delete ckg.re 123456
#+end_src

Each direct change first writes a protected snapshot under
=$HOME/.local/state/dns-bunny/backups=.  Review the snapshot path printed by the
command.  Use =--backup-dir /absolute/path= before the command to override it.

For repeatable or scripted reconciliation, create a project declaration and
its protected key:

#+begin_src sh
cp records.example.json records.json
# Edit owner, zone, paths, and records before continuing.
./dns_bunny.sh init-key /absolute/path/to/bunny-api-key
./dns_bunny.sh check records.json
./dns_bunny.sh plan records.json
#+end_src

Review the complete plan.  The first DNS change is explicit:

#+begin_src sh
./dns_bunny.sh apply records.json
./dns_bunny.sh verify records.json
#+end_src

* Requirements

- A POSIX =/bin/sh=, =stat=, =mktemp=, and ordinary POSIX tools.
- Node.js 18 or newer and the pinned official Bunny OpenAPI client installed by
  =npm ci --ignore-scripts=.  Node is available through pkgsrc in SmartOS
  native zones; the program also checks =/opt/local/bin/node= and the SmartOS
  global-zone =/opt/tools/bin/node= when it is absent from =PATH=.
- jq 1.6 or newer.  The declaration validator checks for the required =IN=
  filter and reports the version floor before reading a declaration.
- macOS, Linux, or SmartOS for direct execution.  Key-file mode inspection is
  selected for Darwin, Linux, and SunOS.
- Network access to =https://api.bunny.net= for =check=, =list=, =add=,
  =update=, =delete=, =plan=, =apply=, =verify=, and =prune=.
- GNU Make for project checks and installation.  Invoke =gmake= on SmartOS.
- An MD5 implementation for project verification and installation updates:
  macOS =md5=, SmartOS =digest=, GNU =md5sum=, or =openssl=.
- Optional =shellcheck= and either =mandoc= or =nroff= for fuller local checks.

On a fresh SmartOS native zone, the missing build/runtime prerequisites can be
installed persistently below =/opt/local= with:

#+begin_src sh
pkgin install nodejs jq gmake
#+end_src

* Record declaration

=records.example.json= is the copyable schema example.  Its top-level fields
are:

- =owner=: a lowercase declaration namespace, unique among independently
  pruned declarations sharing a zone.  Letters, digits, dots, underscores, and
  hyphens are accepted.
- =zone=: the existing Bunny DNS zone name.
- =key_file=: an absolute path to a protected, one-line Bunny account API key.
- =backup_dir=: an absolute path for protected pre-change zone snapshots.
- =records=: a list of desired records.  An empty list is valid, which is
  useful for explicitly pruning all records owned by this declaration.

Every record requires a unique lowercase =key=, a =type=, a zone-relative
=name=, and a non-empty =value=.  Use =@= or an empty string for the zone apex.
Optional fields are =ttl=, =priority=, =weight=, =port=, =flags=, =tag=,
=disabled=, and =allow_multiple=.  TTL defaults to 60 seconds and numeric
routing fields default to zero.

Supported standard record types are =A=, =AAAA=, =CNAME=, =TXT=, =MX=, =SRV=,
=CAA=, =PTR=, =NS=, =SVCB=, =HTTPS=, and =TLSA=.  Bunny's Redirect, Flatten,
PullZone, and Script records require product-specific fields and are
deliberately outside this declaration format.

Set =allow_multiple= to =true= only when a new value should join an existing
unmanaged record set with the same name and type.  It never bypasses CNAME
exclusivity.

* Commands

- =validate=: check the local JSON without reading the key or using the network.
- =check=: verify dependencies, key protection, API access, owner, and exact
  zone lookup.
- =list ZONE=: show every current record and its numeric ID without requiring a
  declaration.  A local file with the same name never changes this meaning.
- =list --records-file RECORDS.json=: read the zone and API-key-file location
  from that JSON records file, then show every current record in the zone—not
  only the records described by the file.
- =add ZONE TYPE NAME VALUE=: create one record from CLI fields.
- =update ZONE RECORD_ID OPTIONS=: change only the named fields of one record.
- =delete ZONE RECORD_ID=: delete exactly one record by its numeric ID.
- =plan=: show =OK=, =CREATE=, =UPDATE=, =REPLACE=, or =CONFLICT= for every
  declared record.
- =apply=: back up the zone, apply a conflict-free plan, and verify the result.
- =verify=: require every declared record to match without changing anything.
- =prune=: after verification, delete only obsolete records for this owner.
- =init-key=: securely prompt for a key and create a new mode-0600 file.

With no arguments, the program prints its version and usage, exits
successfully, and has no side effects.

Global options go before the command.  =--api-key FILE= selects an absolute
protected API-key file.  =--backup-dir DIR= selects an absolute directory for
backups before direct changes and also overrides a declaration's =backup_dir= for
that invocation.

The direct =add= command accepts =--ttl=, =--priority=, =--weight=, =--port=,
=--flags=, =--tag=, =--disable=, and =--enable=.  =update= also accepts
=--type=, =--name=, and =--value=.  Use =@= for the apex.  The supported record
types and field limits are the same as in a JSON declaration.

After =add=, verification requires every submitted field to match.  Fields
that the add request does not submit, such as Bunny-assigned automatic-SSL
state, are accepted rather than compared with invented defaults.  Updates and
identity replacements remain strict because they submit and preserve those
advanced fields.

=update= and =delete= use the exact numeric ID printed by =list=.  This is
intentional: a name and type are not unique because DNS record sets commonly
contain several values.  A name or type change uses a backed-up
delete-then-create replacement and may receive a new ID.

After =delete= fetches the zone and confirms that the ID is absent, its final
output reproduces the deleted record's public =list= summary.  The operator can
therefore see the exact type, name, value, TTL, routing fields, and disabled
state that were removed without exposing its ownership comment.

An update also preserves writable Bunny fields that the direct CLI does not
configure, including acceleration, monitoring, smart-routing, geolocation,
environment-variable, and automatic-SSL settings.  The same preservation
applies when a name or type change requires a replacement record.

Direct commands act on the selected ID even when its comment marks it as owned
by a JSON declaration.  =update= preserves that comment, so the next =plan=
will report and can reverse a value changed outside the declaration.  A later
=apply= can recreate a directly deleted declared record.

* Ownership and project isolation

The ownership comment is the durable identity:

#+begin_example
managed-by:example-project; key=web-origin
#+end_example

Choose one stable =owner= per independently pruned declaration.  Reusing an
owner in two declarations would let either declaration prune records omitted
from itself.  Changing an owner makes the old records look unmanaged; it is not
a rename operation.  Duplicate ownership comments and ambiguous unmanaged
matches are conflicts, so the tool stops before making changes.

An exact unmanaged record may be adopted by adding the ownership comment.
Changing an owned record's name or type uses delete-then-create because Bunny's
record update endpoint does not reliably apply identity changes.  The backup
is the recovery reference for that non-atomic replacement.

=apply= and =prune= are single-writer operations.  Do not edit the same Bunny
zone through another process, API client, or dashboard while either command is
running.  The post-apply fetch detects a divergent declared state but cannot
lock the zone or prevent another writer from racing an individual API request.

For a declaration migrated from the original Matrix repository, add:

#+begin_src json
"owner": "matrix-server"
#+end_src

That value preserves the existing =managed-by:matrix-server; key=...= comments.

* Credentials and backups

The API key file must be a regular, non-symbolic file with mode 0400 or 0600.
It must contain exactly one line of printable ASCII with no leading or trailing
space.  The official-client helper reads that protected file directly.  The
secret is not copied to a temporary file, environment variable, shell history,
or process argument; only the key-file path is passed to the helper.  Temporary
request bodies and API responses are removed on normal exit and on handled
HUP, INT, or TERM signals.  SIGKILL cannot run shell cleanup, so a protected
mode-0700 =dns_bunny.*= directory containing DNS data may remain under =TMPDIR=
after such a termination.

Direct commands default to =$HOME/.secrets/bunnynet-api-key=.  The global
=--api-key /absolute/path= option selects a different file.  Despite its short
name, this option takes a path, never the secret value, so the credential does
not enter shell history or process arguments.

On the SCS workstation, the existing Bunny API key can be found at
=~/.secrets/bunnynet-api-key=.  The file was verified as a regular,
non-symbolic mode-0600 file on 2026-08-29.  JSON does not expand =~=, so an SCS
project declaration must use the full path:

#+begin_src json
"key_file": "/Users/scs/.secrets/bunnynet-api-key"
#+end_src

Do not commit the key.  Keep it on the trusted operator machine and do not copy
it to a public application server.

Before =add=, =update=, =delete=, =apply=, or =prune= changes anything, the full
current zone document is saved.  Direct commands default to
=$HOME/.local/state/dns-bunny/backups=; declarations use =backup_dir=.  The
directory is mode 0700 and each snapshot is mode 0600.  Timestamp and process
ID are included in the filename, and an existing name is never overwritten.
API changes are sequential and are not rolled back automatically after a
later request fails; use the snapshot to inspect and recover a partial run.

* Installation

The default target is read-only:

#+begin_src sh
gmake
gmake show-install-paths
#+end_src

Prepare the exact, locked runtime once after checkout or archive extraction:

#+begin_src sh
npm ci --ignore-scripts
#+end_src

On macOS, =gmake install= places the executable in =$HOME/bin=, the helper and
official-client runtime in =$HOME/libexec/dns-bunny=, and the manual page in
=$HOME/share/man/man1=.  A SmartOS global-zone install uses the corresponding
=/opt/custom= paths.  A SmartOS native-zone install uses =/opt/local=, keeping
the application and dependencies out of the small global-zone =/root= memory
filesystem.

Use =gmake update= for an existing installation.  It compares the source and
installed shell script, Node helper, and dependency lockfile by MD5 rather than
trusting their version strings.  If all three are identical, it reports that no
update is needed and changes nothing.  If any differ, it prints the installed
and incoming versions and component MD5 values, then runs =uninstall= followed
by =install=.  A missing installed script is treated as a first installation.

Override logical destinations with absolute paths:

#+begin_src sh
gmake install BINDIR=/usr/local/bin \
  LIBEXECDIR=/usr/local/libexec/dns-bunny \
  MANDIR=/usr/local/share/man/man1
#+end_src

Use an absolute =DESTDIR= to stage a package without writing to live locations:

#+begin_src sh
gmake install DESTDIR=/tmp/bunny-dns-stage
gmake uninstall DESTDIR=/tmp/bunny-dns-stage
#+end_src

=uninstall= removes only =dns_bunny.sh=, =dns_bunny.1=, the installed helper,
its runtime metadata, and the three dependency package trees installed by this
project.  It preserves their containing directories.

=dns_bunny.sh.md5= and =dns_bunny_node.mjs.md5= are source-tree sidecars in the
usual =checksum  filename= form.  =gmake check= validates both, and
=gmake checksum= refreshes them after reviewed script changes.  The sidecars
are not installed: =update= computes live checksums independently.  MD5 is used
here only to detect equality and accidental corruption; it is not a signature
and does not authenticate the source.  The SHA-512 package integrity values in
=package-lock.json= authenticate downloads performed by npm.

For a later import into an SVN vendor directory, keep release sources and npm
dependencies as pinned =.tgz= or =.zip= archives with checksums rather than an
exploded =node_modules= tree.  SVN externals are not a good match for immutable
npm registry archives.  No SVN checkout is created or modified by this
repository's installer.

* Future plans and possibilities

** Scoped Bunny API gateway

Future gateway work should use the
[[https://github.com/sipico/bunny-api-proxy][sipico/bunny-api-proxy Git repository]]
as its primary reference.  The project is a long-running Go and SQLite gateway
that issues zone-, action-, and record-type scoped local tokens.  That can be
valuable when untrusted ACME or deployment clients must not hold a Bunny
account key.

** Why it is not bundled today

It is not a replacement for declarative reconciliation, backups, conflict
detection, or per-project ownership.  The review for this import used upstream
commit =20f4f0504c9a324f3b5efed3b748b0ec895d7f33=.  At that revision there was
no tagged release, and the checked-in quickstart/configuration files did not
fully agree with the current program requirements.  This repository therefore
talks to Bunny directly and carries no proxy runtime.  A future deployment may
place a reviewed, pinned proxy in front as a separate service after its API
compatibility and TLS boundary are verified.

* Development and verification

Run:

#+begin_src sh
npm ci --ignore-scripts
gmake checksum       # after reviewing a change to either script
gmake self-check
#+end_src

The offline suite uses a stateful fake official-client helper.  It exercises unambiguous
direct and declaration listing, adding, partial updating, advanced-field
preservation, identity replacement, deletion, JSON validation,
planning, fail-closed plan construction, adoption, reconciliation,
owner-isolated pruning, protected backups, lookup failures, the jq feature
floor, and Darwin/Linux/SunOS key-mode branches without using a real account.

The project also checks checksum validation and staged install, no-op update,
content-drift update, and uninstall behavior during release verification.  A
live Bunny API call is intentionally not part of the offline suite; run =check=
and =plan= against a reviewed project declaration before the first real
=apply=.
